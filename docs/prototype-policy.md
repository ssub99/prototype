# 프로토타입 정책

새 세션이나 새 화면을 작업할 때 먼저 읽는 문서. (논페이지 정책은 `docs/none-page-policy.md`)

## 1. 구조
- 루트 `index.html`: 개선 전 / 개선 후 선택 화면. 각 버전은 `before/`, `after/` 폴더.
- `common/`: 두 버전이 함께 쓰는 모듈 — `data.js`(데이터), `onboarding.js/css`(공통 레이아웃·헬퍼), `none-page.js`(논페이지+가이드), `class-fee.js`(클래스 수강료), `time-picker.js`(시간 설정 시트·휠), `ym-picker.js`(청구년/월 시트), `invoice.js`(청구서 데이터·계산), `home-chip.js`(우하단 컨트롤).
- `ds/`: 디자인 시스템(바닐라 JS, `window.Rallyz`). 수정 후 재빌드 순서: `node ds/build-figma.mjs` → `node ds/build-browser.mjs`. 아이콘은 반드시 SVG(피그마에서 추출).
- 화면은 피그마를 먼저 확인한 뒤 구현한다(선택한 프레임 기준). 구현 후 피그마 이미지와 나란히 비교하고, 흐름은 브라우저 테스트로 눌러서 확인한다.

## 2. 개선 전 / 개선 후
- 개선 전 디자인이 없는 화면은 개선 후 화면을 그대로 복사해 쓴다. 복사본은 `<title>`만 다르다(`Rallyz(개선 전) — …`).
  - 동일 복사본: `index`, `onboarding-intro`, `onboarding-academy`, `home`, `academy-main`, `academy-manage`, `class-manage`, `student-list`, `student-manage`, `student-add`, `attendance`, `invoice-create`, `invoice-adjust`, `invoice-confirm`, `invoice-progress`, `invoice-done`, `student-detail`, `feed`, `feed-write`, `feed-detail`, `payment-manage`, `payment-confirm`, `payment-progress`, `payment-done`. 한쪽을 고치면 **같은 작업에서 반대쪽도 똑같이** 고친다(`sed 's#<title>Rallyz — X</title>#<title>Rallyz(개선 전) — X</title>#' after/F > before/F`).
  - **별도 파일(UI·로직이 다름)**: `class-create`(온보딩 클래스 만들기), `class-new`(클래스 생성), `class-edit`(클래스 수정), `student-register`, `academy-done`, `class-done`. 입력 규칙을 바꾸면 양쪽을 각각 고친다. 개선 후 전용: `student-done`.
- 개선 전 클래스 만들기(`before/class-new` 1·2단계, `before/class-create`)는 학원명 제목 위·아래 여백이 각각 48px이다(수정 화면은 그대로).
- 개선 전 `class-new`/`class-edit`은 개선 전 온보딩 UI(과목 드롭다운 + 선택 버튼, 요일 원형 칩)를 쓰되 **단계 구성과 입력 항목은 개선 후와 동일**하다.

## 3. 데이터
- `RzData`(`common/data.js`): 버전별로 sessionStorage에 저장(`rz.data.<version>`). 화면에는 온보딩에서 입력한 **실제 값**을 보여준다(디자인의 더미 데이터를 쓰지 않는다).
- 클래스 저장 필드: `name, subjects[소분류], features[], schedules[{days,time}], teacher, teacherPhone, type, intro, thumb, photos, fee, perFee, sessions, show`. 학생: `name, phone, guardian, klass, …`. 출석: `attendance[날짜][학생 인덱스]`.
- 클래스 이름을 바꾸면 그 클래스의 학생도 새 이름으로 따라간다. 클래스를 삭제하면 학생은 남고 클래스 미배정(`klass: ""`)이 된다.
- 썸네일은 홈에서 클래스마다 무작위 5종 중 배정(업로드한 대표사진이 있으면 그것).

## 4. 화면 공통 원칙
- 상태바와 헤더는 고정, 본문만 스크롤.
- **구현하지 않은 퍼널(디자인 없음)에는 링크·동작을 걸지 않는다.** 확인 모달 같은 후속 디자인이 없을 때도 임의로 만들지 않고 보고한다. (현재 미연결: 클래스 관리 ⋮ › 보강·출석 시간 변경 외 일부, 수업 지원의 다른 메뉴, 정렬 변경, 날짜 선택, 다운로드 파일 생성, 수강료 불러오기, 초대 등)
- 디자인에서 "선택된 상태"로 그려진 요소도 처음 진입 시에는 기본(미선택) 상태로 시작한다. 확정된 예외: 대표 이미지는 기본 이미지 탭에서 1장 무작위 선택.
- 필수 항목 표기는 라벨 옆 "필수". 비어 있으면 확인 모달로 안내하고 해당 항목으로 스크롤.
- 클래스·학생이 없을 때의 빈 상태는 논페이지 정책을 따른다(요청한 화면에만 적용, `needs` 필수 지정).
- **학원관리 닫기(개선 전/후 동일)**: 학원 메인(`academy-main`)의 학원관리로 들어왔으면 닫기는 **학원 메인**으로 간다(클래스·학생 관리 등을 거쳐 돌아와도 유지, `?from=academy-main` + 세션 값 `manageFrom`). 홈의 학원관리로 들어왔으면 홈으로 간다. **학원 메인의 닫기는 항상 홈**(push)이다 — 뒤로 가기로 하면 홈 → 학원 메인 → 학원관리 → 학원 메인 → 학원관리 …가 반복된다. 그 밖의 경우는 아래 규칙.
- **개선 전: 학원관리 닫기는 항상 홈**으로 보낸다(`go`, push). 논페이지 → 클래스/학생 만들기 → 클래스 관리/학생 관리 → 닫기 → 학원관리에서 다시 닫을 때 `history.back()`이면 방금의 관리 화면이 다시 뜨는 문제가 있어서다(개선 후는 이전 화면으로 돌아가는 기존 동작). 관리 화면으로 가는 이동은 모두 `go()`(push)다.
- **논페이지에서 만든 뒤 어디로 가는가(개선 전/후가 다르다)**: 개선 후는 만들기를 끝내면 **원래 화면(`from`)으로 돌아와** 다음 논페이지(또는 실제 화면)를 보여 준다. 개선 전은 **그 항목의 관리 화면으로 보낸다** — 클래스 만들기 완료 → 클래스 관리(`class-manage`), 학생 등록 완료 → 학생 관리(`student-manage`). 닫기·이전(X)은 두 버전 모두 원래 화면으로 돌아간다. (`before/class-new`, `student-add`의 `RzData.version === "before"` 분기)

## 5. 입력 규칙 (클래스 만들기 / 수정, 온보딩 포함 · 개선 전/후 공통)
- **과목 분류**: 최대 5개. 개선 후는 대분류/소분류 목록에서 선택, 선택한 과목은 "대분류 | 소분류 ✕" 행으로 표시. 개선 전은 드롭다운 2개 + 선택 버튼.
- **클래스 특징**: 최대 10개.
- **수업 일정**: 개선 후 — 요일을 고르면 "종일" 켜짐, 종일을 끄면 시간 입력. 개선 전 — **시간 필수**(시간 없이 추가하면 "수업 시간을 모두 입력해 주세요." 모달). 필수 표기는 "필수"만(시간 필수는 표기하지 않음).
- **시간 설정**: 바텀시트(시/분 휠, 24시간제, 00↔59·23↔00 무한 루프, `common/time-picker.js`). 시작·종료 규칙: 종료는 시작보다 늦어야 하고 같은 시각도 불가, 어긋나면 모달("종료 시간은 시작 시간보다 늦어야 합니다." / "시작 시간은 종료 시간보다 빨라야 합니다.")로 알리고 값은 적용하지 않는다. 밤을 넘기는 수업은 미지원.
- **클래스 유형(필수)**: 기간반/회차반, **기본 선택 없음**. 비어 있으면 모달("클래스 유형을 선택하세요.")로 안내하고 해당 항목으로 스크롤. 클래스 수강료 입력칸은 유형을 고른 뒤에 나타난다. 온보딩·학원관리(생성/수정) 개선 전/후 모두 동일하며 구현은 `common/class-fee.js`(`fee.typeField`) 한 곳. 청구서 생성의 "클래스 구분"(기간반/회차반)이 이 값을 쓴다.
- **클래스 수강료(필수)**: 기간반 = "클래스 수강료" / 회차반 = "1회 수강료" + "수업 회차"(둘 다 필수). 0·빈 값은 미입력으로 보고 모달("클래스 수강료를 입력하세요." 등). 온보딩에서는 수업 일정 바로 아래(필수 항목 마지막)에 배치하고, 아래의 클래스 유형 선택에 따라 전환. 구현은 `common/class-fee.js` 한 곳.
- **강사 불러오기** 목록: 김강사(010-1234-1234), 송강사(010-5678-5678).
- **학생 등록**: 탭 UI(개별/일괄) 없음 — 개별 등록 폼만. 온보딩 학생 등록은 개선 전/후 별도 화면, 학원관리 학생 등록(`student-add`)은 공통.
- **클래스 삭제**: 확인 모달("아니오/예", 문구는 복사 확인 모달과 같은 형식) → 삭제. (삭제용 피그마 모달이 생기면 교체)
- **클래스 복사**: 확인 후 원본 바로 아래에 "{이름} 사본"(학생은 이동하지 않음).

## 6. 출석 관리 (`attendance`)
- 진입: 학원관리 › 학원 출석 관리. 클래스·학생 모두 필요(논페이지 → 클래스 먼저, 다음 학생).
- 타일(전체·미처리·출석·조퇴·결석)로 필터. 출석/결석 버튼, 출석한 학생은 "종료" 버튼.
- **수업 종료**: 출석 처리된 학생 중 종료·조퇴·결석이 아닌 학생에게만 종료 시각 기록. **전원 출석**: 확인 후 미처리 학생을 출석 처리.
- ⋮ 메뉴: 메모(시트) · 조퇴 · 지각(토스트) · 보강(동작 없음) · 출석 시간 변경(시간 설정 시트) · 출석 취소.
- 클래스 선택 UI는 디자인에 없어 학원 전체 학생을 한 목록으로 보여준다.

## 6-1. 청구서 (`invoice-create` · `invoice-adjust` · `invoice-confirm` · `invoice-progress` · `invoice-done`)
- 진입: 학원관리 › 청구/납부 › 청구서 생성. 개선 전 디자인이 없어 양쪽 동일 복사본. 클래스·학생 모두 필요 → 클래스 → 학생 순 빈 상태(이 화면 전용 문구, 디자인 351:150316/150363/150409).
- 흐름: **진입하면 조회하지 않고** 청구년월·클래스 구분(기간반/회차반)부터 고른다("청구서를 생성할 클래스를 선택하세요"). 조정·확인·완료에서 돌아올 때(`?keep=1`)만 직전 선택을 이어간다. → 전체 클래스·검색으로 학생 목록. 청구월은 ◀ ▶ 또는 제목 탭(청구년/월 시트). 기본 청구월은 오늘 기준.
- 금액: 클래스 수강료(`fee`, 회차반은 1회 수강료×회차)를 기준으로 계산. 표기 "청구금액 N원(M개월)" / 회차 클래스 "(N회)". 납부기한은 청구월 말일.
- 생성: 학생 체크 → 선택 항목 생성(0건이면 비활성), 전체 일괄 생성은 현재 목록의 미생성 학생 전체. 생성된 학생은 체크 비활성 + "추가 생성"(추가청구서가 같은 박스 안에 붙음).
- **선택 항목 생성**(디자인 360:158248 외 6장): 선택한 미생성 학생 → `invoice-confirm`(N명·N월 확인, 수강기간 시작일/종료일(바텀시트 캘린더 `common/due-picker.js`, 제목 "시작일 선택"/"종료일 선택")·수강기간 없음·알림 발송 체크, 종료일 비면 "종료일을 입력해 주세요.") → 예 → `invoice-progress`(작업중, 2초 뒤 자동 이동, 학원관리 바로가기) → 실패 없음: `invoice-done`(생성 완료: 청구서 목록으로 → 청구서 생성, 납부관리 바로가기 → 납부 관리) / 실패 있음: 청구서 생성 목록 위에 "청구서 생성결과" 시트(성공(N)/실패(N) 탭에 클래스 칩). 청구금액이 0원인 학생은 생성 실패로 처리(실패 탭에 클래스 표시). 전체 일괄 생성은 디자인이 없어 확인 없이 바로 생성.
- 조정(미생성 카드만): 수강료 미청구, 할인(원/% 전환: %는 클래스 수강료 대비 비율(최대 100), 원은 절대 금액(최대 수강료); 단위를 전환하면 같은 할인액으로 환산), 청구 개월 분(기간 클래스만), 할인 사유와 계속/이번만 적용, 기타경비(최대 10개). "계속 적용" 할인은 이후 달에 이어진다. 저장은 `RzData.adjusts`.
- **조정/추가 생성 모달**(351:149540 · 149625 · 149710 · 149795 · 150623 · 150689 · 150755): 저장 시 입력 검사(납부기한 → 기타경비 항목명 → 금액, 알럿) 후 컨펌("OO 학생의 청구서 내역을 저장하시겠습니까 ?" / 추가 생성은 "OO 학생에게 청구서를 추가로 생성하시겠습니까 ?"). 변경 후 < 로 나가면 "작성완료되지 않았습니다 … 저장하지(추가하지) 않고 이전화면으로 이동하시겠습니까 ?" 컨펌. 조정 저장 후 목록에 토스트("청구서 정보가 저장되었습니다.", 출석 관리 토스트 296:127932와 같은 모양, 2초). **추가 생성**은 조정 화면(`?mode=extra`)에서 작성 → 컨펌 → 추가청구서 생성.
- **조회 기준**(375:162750): 목록의 "전체내역"을 누르면 시트(전체내역·미생성·생성완료·납부완료 다중 선택, 전체내역은 단독) → 적용. 상태는 본 청구서 기준(미생성 = 본 청구서 없음, 생성완료 = 생성됐고 미납, 납부완료 = 납부됨). 진입 시 전체내역으로 초기화, 돌아올 때(`?keep=1`)만 유지.
- **납부기한 선택**(375:162478): 청구서 생성 목록의 미생성 카드 납부기한, 조정 화면 상단 카드의 납부기한을 누르면 캘린더 시트(`common/due-picker.js`) → 저장. 이미 생성된 청구서의 납부기한은 바꿀 수 없다. 변경값은 조정 저장(`adjusts.due`)에 들어가고, 확인 화면·생성되는 청구서의 납부기한에 반영된다(기본 청구월 말일).
- 미연결(디자인 없음): TIP, 납부 처리, 청구년/월 직접 입력(키보드 버튼).
- 디자인 불일치로 정한 것: 학생 없음 빈 상태 버튼은 디자인엔 "클래스 만들기"지만 문구에 맞춰 "학생 등록하기"로 구현. 학생 이름 옆 관리용 이름(예: 김티모)은 데이터가 없어 생략. 회차 클래스도 조정 화면을 공유(청구 개월 분만 숨김).

## 6-2. 납부 관리 (`payment-manage` · `payment-confirm` · `payment-progress` · `payment-done`)
- 진입: 학원관리 › 청구/납부 › 납부 관리. 개선 전 디자인이 없어 양쪽 동일 복사본. 목적: 생성된 청구서를 관리(납부요청 발송, 이후 생성취소).
- **진입 시 선택부터**: 청구서 생성과 같이 청구년월 카드 + 클래스 구분(기간반/회차반) + 전체 클래스를 고르기 전에는 조회하지 않고 "납부 내역을 조회할 클래스를 선택하세요"를 보여준다. 선택한 청구월·유형의 미납만 나오고, 일괄 발송·확인에서 돌아올 때(`?keep=1`)만 선택을 유지한다.
- 미납 목록(`unpaid()` = `RzData.invoices` 중 납부 안 된 청구서): 클래스 필터, 학생 검색, 카드 체크박스. 카드 = 이름 · 클래스(유형) · 청구월 · 미납금액 · 생성일/발송일/납부기한(기한 지나면 빨강) · 수강기간(있을 때).
- **납부요청 버튼(개선 후)**: 기본은 비활성(회색), 항목을 하나 이상 체크해야 활성화된다 — 그래서 개선 후에서는 선택 없는 일괄 발송에 들어갈 수 없다. 개선 전은 기존 동작.
- **납부요청**: 선택한 청구서가 있으면 선택 발송 확인(`payMode=sel`), 선택이 없으면 **미발송 전체 일괄** 확인(`payMode=all`, 일러스트 `assets/onboarding/invoice-bulk.svg`). 대상이 없으면 "발송할 청구서가 없습니다." 알럿(디자인 없음). 예 → 발송일(`sentAt`) 기록 → 작업중(2초) → 전원 성공이면 발송 완료 화면, 실패가 있으면 납부 관리 위에 "청구서 납부요청 결과" 시트(성공/실패 탭, 클래스 칩).
- **생성취소**: 선택한 청구서 → 컨펌 알럿("선택하신 미납 청구서를 생성 취소합니다…", 아니오/예) → 예 → 청구서 삭제 + 완료 알럿. 취소된 청구서는 청구서 생성 목록에서 다시 미생성 상태가 되어 재생성할 수 있고, 본 청구서를 취소하면 같은 학생·청구월의 추가청구서도 함께 취소된다. 선택 없이 누르면 "취소할 청구서를 선택하세요."(디자인 없음).
- 발송 실패 조건: 학생·학부모 연락처가 모두 없는 학생(`Invoice.sendable`).
- 미연결(디자인 없음): 납부 완료 탭, 납부처리, 상세보기, 정렬/기간 필터/다운로드, TIP. 내역 없음 논페이지(360:162383): 미납이 하나도 없거나 클래스·검색 조건에 맞는 내역이 없으면 "조건에 맞는 미납 내역이 없습니다."(일러스트, 버튼 없음). 월 카드·탭·필터·TIP은 유지하고 선택 개수 바와 하단 버튼은 숨긴다.

## 6-3. 학생 명단 · 회원 상세 (`student-manage?class=` · `student-detail`)
- **학생 명단**(375:163209): 클래스 관리 › ⋮ › 학생관리(`student-manage.html?class=<name>`)에서 열린다. 헤더 "학생 명단" + 클래스명, 검색만(클래스 선택·엑셀·일괄 초대 없음). 학생 행은 › 로 회원 상세로 이동.
- **보호자 행은 보호자 연락처를 등록한 경우에만** 학생 아래에 붙는다(학생만 등록하면 학생만 보인다). 학생 휴대폰 칸이 비어 있으면 학생 행 연락처는 "-"이고, 보호자 번호를 학생 번호로 복사해 넣지 않는다(`student-add`).
- **회원 상세**(375:163032): 학생정보 탭(출석현황·학습 보고서·상담이력 탭, 편집, 추가/수정, 클래스 이동, 납부일 저장, 하단 바로가기는 동작 없음). **삭제**(클래스 영역 버튼 줄의 빨간 버튼, 클래스가 없으면 단독으로)는 확인 모달 후 이 학생을 학원에서 지운다 — 학생 목록에서 빠지고 그 학생의 청구서·조정·출석·피드 읽음 기록도 함께 정리되며 뒤 학생들의 번호 참조는 당겨진다(`RzData.removeStudent`). **클래스에서 제외**는 눌러서 이 학생의 소속 클래스를 비운다(클래스 미배정, `klass: ""` — 소속 클래스 영역에서 카드가 사라지고 클래스별 목록·청구서 대상에서도 빠진다). 값은 등록한 실제 데이터이고 없는 값은 "-"/"미입력", 형제/자매 연결정보는 데이터가 없어 생략한다.

## 6-4. 피드 (`feed` · `feed-write` · `feed-detail`)
- 진입: 홈 › 오늘의 피드 "전체 피드 보기" 또는 하단 내비 피드 탭. 개선 전 디자인이 없어 양쪽 동일 복사본. 공용 데이터·조각은 `common/feed.js`(+`feed.css`), 표정 5종은 Figma에서 SVG로 뽑은 `assets/feed/emoji-1~5.svg`.
- **전체 피드**(360:152570): 검색(내용·태그), 카드(학원·클래스, 작성자, "N명 읽음" → 읽은 사람 시트(360:152415), 표정·댓글 수). 검색 결과 없음(360:152541) 문구는 시안 그대로, 피드가 하나도 없을 때는 디자인이 없어 "등록된 피드가 없습니다."만 둔다. 홈의 오늘의 피드는 오늘 올린 글이 있으면 최근 3개를 카드로 보여 준다.
- **작성된 피드가 하나도 없으면 검색 영역을 보여 주지 않는다**(클래스 논페이지·"등록된 피드가 없습니다." 모두, 개선 전/후 동일). 피드가 있으면 검색이 보이고, 검색 결과가 없을 때도 검색은 유지된다.
- **전체 피드 본문에 클래스가 없으면** "등록된 피드가 없습니다." 대신 클래스 논페이지(`needs ["class"]`, `from=feed`)를 보여 준다(헤더·내비는 유지, 검색 영역은 아래 규칙대로). 개선 전은 버튼 아래 텍스트 버튼 없음, 개선 후는 있음. 클래스를 만든 뒤 개선 후는 피드로 복귀, 개선 전은 클래스 관리로 간다.
- **글쓰기에 클래스가 없으면** 글쓰기 폼 대신 클래스 논페이지(`needs ["class"]`, `from=feed-write`)를 보여 준다 — 개선 전은 버튼 아래 텍스트 버튼 없음, 개선 후는 있음(NonePage가 버전별로 그린다). 클래스를 만든 뒤 개선 후는 글쓰기로 복귀, 개선 전은 클래스 관리로 간다.
- **글쓰기**(360:152996): 글만 작성한다 — 갤러리·파일 업로드, 조회 대상 선택은 구현하지 않아 하단 바는 동작 없음. 단축태그(# 과제 · # 공지)와 직접 입력(# 태그 입력 + 입력/Enter)으로 태그 추가·삭제(중복·빈 값 무시). 완료는 내용이 있어야 켜지고, 저장 후 전체 피드로 간다. 클래스는 `?class=` 없으면 첫 클래스.
- **글 상세보기**: 표정(+로 5종 중 선택 — 시안에 없는 최소 팝오버, 한 사람 한 표정, 표정 시트 360:153928), 댓글·답글(비밀댓글, ⋮ 수정/삭제, 삭제는 "댓글/답글이 삭제되었습니다."로 남음, 답글쓰기·수정 모드), 파일 업로드는 동작 없음. 현재 사용자는 학원장(`Feed.me()`)이라 "비밀댓글 권한 없음"은 나타나지 않는다.
- **읽은 사람 보기**: "N명 읽음" → 읽음/읽지 않음 탭, 학생·보호자 그룹(접기/펼치기), 읽지 않음에는 전체 알림(확인 모달 → "알림이 발송되었습니다." 토스트)·채팅하기(채팅 대상 목록 시트, "채팅방 입장"은 채팅 미구현이라 동작 없음)·개별 알림/채팅. 학생·보호자 쪽 사용자가 없어 읽음은 글 등록 시 대상(그 클래스 학생 + 보호자) 중 일부를 읽은 것으로 만든 **모의 데이터**다.

## 7. 프로토타입 컨트롤 (`common/home-chip.js`)
- 지문 패널(목업 왼쪽)은 안의 내용 묶음(검정 박스 ~ 컨트롤)을 패널 높이 기준 **세로 가운데**에 둔다(내용이 넘치면 위에서부터 스크롤).
- 지문 패널(목업 왼쪽): 검정 박스 **바로 아래에 한 행** — 왼쪽 "유형" 텍스트, 오른쪽 [개선 전/후 토글] — 이 행은 어코디언을 접어도 항상 보인다. 어코디언 영역은 한 행으로 왼쪽에 [접기], 맨 오른쪽에 **설문** 버튼(상단 검정 박스와 같은 배경 + 흰 글자, 구글 폼을 새 창으로 연다)이 있고, 접히는 건 버튼 줄뿐이다: [새로고침](순환 아이콘 + 텍스트, 지금 화면을 다시 불러온다, 가장 왼쪽) [처음으로 · 메인으로 · 이전페이지 · **데이터 초기화** · **컨벤션 ↗**(흰색 버튼, 컨벤션 메인을 새 창으로 연다)] — 데이터 초기화 버튼은 확인 모달 후 지금 보고 있는 버전의 입력 데이터·스톱워치만 지우고 그 버전의 온보딩부터 다시 시작한다(다른 버전 데이터는 유지; 처음으로는 두 버전 모두 지움). 지문 박스 아래에는 어코디언과 한 줄의 [처음으로 · 메인으로 · 이전페이지]. 창이 좁아 지문 패널이 숨겨지면 같은 컨트롤이 우하단(우·하 32px)에 뜬다. 어코디언 버튼은 지문 박스 바로 아래에 있고, 컨트롤(개선 전/후·데이터 초기화·버튼 줄)은 그 버튼 바로 밑에 이어 붙으며 버튼으로 접고 펼친다(상태는 세션 동안 유지). **목업 크기**: 브라우저 높이(위아래 여백 80px 제외)와 폭에 맞춰 지문 영역과 목업을 같은 비율로 줄인다(최대 100%, 확대 안 함). 지문 첫 줄은 헤더 크기(Headline/Bold 20px), 지문 박스 문장은 Headline/Bold 20px(번호도 같은 굵기·검정, 색 없음), 안내 문장은 16px. **컨벤션**: 어코디언 옆 "컨벤션 ↗" 버튼이 컨벤션 메인(루트 `index.html`, 디자인 시스템 링크가 있는 첫 화면)을 새 창으로 연다. 지문별로 정지해 저장된 시간이 localStorage(`proto.conv`)에 회차별("처음으로" 사이의 한 번의 진행)로 쌓이고, 컨벤션 메인의 "지문별 소요 시간" 표(회차·버전·지문별 시간·합계·저장 시각·평균)로 조회한다(다른 창에서 저장되면 자동 갱신, "기록 모두 지우기" 가능). **스톱워치**: 지문 박스마다 오른쪽에 하나씩(지문별 독립, 지문 영역 너비 580px로 넓힘))에 NN:NN · 재생 · 일시정지 · 정지. 정지하면 그 지문의 재생·일시정지·정지가 비활성화되고(정지 오른쪽 **초기화** 버튼은 시작 후 언제든 눌러 00:00으로 되돌리며 저장된 컨벤션 기록도 지운다) 시간이 멈추며 "저장됨" 표시와 함께 그 시간이 지문별로 저장되고, 상태는 **개선 전/후가 따로** 저장되어(전환해도 서로 섞이지 않고 각각 쌓인다, 컨벤션 회차도 버전별) 화면 이동에도 이어지고 "처음으로"에서 리셋된다.
- 토글: 확인창 없이 바로 전환한다. **개선 전/후 데이터는 따로따로다** — 전환해도 데이터를 복사하지 않고 전환할 버전이 가진 자기 데이터를 그대로 쓴다(학원이 이미 있으면 그 버전의 홈, 아직 없으면 온보딩 첫 화면). 입력 데이터(`rz.data.<버전>`)·화면 사이 임시 값(`rz.<버전>.*`)·스톱워치·컨벤션 회차가 모두 버전별이고, **데이터 초기화는 켜져 있던 유형(지금 보고 있는 버전)만** 지운다. 처음으로는 두 버전 모두 지운다.
- **지문 패널**: 목업과 같은 크기(395×832) 영역을 목업 왼쪽에 잡고 **지문 영역 + 목업을 한 묶음으로 화면 가운데에 정렬**한다. 지문은 박스 한 줄씩 보여준다(첫 박스 = 역할·상황 설명, 이후 번호 매긴 지령 박스). 내용은 `common/scenario.js`의 `RZ_SCENARIOS.before / .after`(intro, steps)만 고치면 된다 — **지문은 버전별로 다르다**(개선 후: 1 학원셋팅 완료(개선 전과 같은 문장), 2 청구서 관리로 청구서 생성, 3 생성된 청구서 발송). 컨벤션 표 아래에 두 버전의 지문이 함께 표시된다. 폭이 약 860px보다 좁으면 패널을 숨기고 목업만 가운데에 둔다.
- 목업이 있는 모든 화면에 자동으로 붙는다. 새 화면에는 `ds/rallyz.browser.js` 다음에 `<script src="../common/home-chip.js?v=52">`만 넣는다(캐시를 피하려고 컨트롤을 고칠 때마다 v 숫자를 올린다)(자체 스타일 포함).

## 8. 열린 항목
- "처음으로"에 확인 모달을 넣을지(지금은 바로 초기화).
- 클래스 삭제 확인 모달의 정식 디자인.
- (결정됨) 주소 입력에 카카오 우편번호 서비스 도입 완료 — 학원 정보 입력의 주소 칸 개선 전/후 적용.

## 시나리오 (1 · 2)

- 지문 패널의 시나리오 칩(시나리오1·2)으로 고른다. 선택은 탭 세션(`proto.scn`)에 저장된다.
- **시나리오끼리는 완전히 독립이다.** 저장 칸은 `버전 × 시나리오` — 시나리오1은 기존 키(`rz.data.<버전>`, `rz.<버전>.*`, `proto.sw.<버전>.*`, `proto.sess.<버전>`), 시나리오2는 `<버전>-s2`를 쓴다. 데이터·화면 간 임시 값·스톱워치·컨벤션 회차 모두 그렇다.
- **데이터 초기화**: 지금 시나리오의 지금 유형(개선 전/후 중 켜져 있는 쪽) 한 칸만 지운다. 같은 시나리오의 다른 유형, 다른 시나리오는 그대로. **처음으로**는 지금 시나리오의 개선 전/후 둘 다(다른 시나리오는 그대로).
- 칩 전환: 같은 유형의 그 시나리오 데이터로 간다(학원이 있으면 홈, 없으면 온보딩 첫 화면). 컨벤션 기록(`proto.conv`)에는 `scenario`가 붙고, 컨벤션 페이지의 시나리오 칩으로 조회한다.
- 시나리오2 지문은 시나리오1과 같은 문구다(`common/scenario.js`의 `RZ_SCENARIOS_2`가 복사본이라 따로 고칠 수 있다). 단 **시나리오2 개선 후는 4번 지문이 더 있다**: "학생 1명을 추가 등록 후 해당 학생의 출석을 진행해 주세요."
- **시나리오2 시작 상태**: 학원만 생성돼 있다(개선 전/후 동일) — "랠리즈 종합학원", 중등·고등 대상, 재원생 50~100명. 클래스·학생은 없다. 데이터 초기화·처음으로 뒤에도 같은 상태(홈)로 시작한다(시나리오1은 온보딩부터).
- **시나리오2 타이틀**: "당신은 중·고등학생들에게 주요 과목을 가르치는 학원장입니다." (시나리오1은 "…수학을 가르치는…"). 개선 전/후 동일.
- **클래스 수강료 기본 노출(개선 전/후, 시나리오 1·2 공통)**: 클래스 만들기·수정의 클래스 유형 바로 아래에 클래스 수강료 입력이 유형을 고르기 전에도 보인다. 회차반을 고르면 1회 수강료 + 수업 회차로 바뀐다(유형은 여전히 필수, 기본값 없음).
- **학원관리 안내 툴팁(개선 후만, 시나리오 1·2 공통)**: 학원관리에 들어오면 해당 항목이 없을 때 DS 툴팁을 띄운다 — 클래스가 1개도 없으면(학생 유무 무관) "클래스" 메뉴 위에 클래스 툴팁("등록된 클래스가 없습니다. 생성해 주세요."), 클래스는 있고 학생이 1명도 없으면 "학생/보호자 관리" 메뉴 위에 학생 툴팁("등록된 학생이 없습니다. 1명 이상 등록해 주세요."). 디자인은 Figma 397:172515의 초록 알약 툴팁(DS 기본 툴팁이 아님). 둘은 동시에 뜨지 않고(클래스 → 학생 순서), 둘 다 있으면 안 뜬다. X 로 닫으면 그 화면에서만 사라지고, 조건이 그대로면 다시 들어올 때 또 뜬다.
- **시나리오2 1번 지문**(개선 전/후 동일): "클래스를 생성하고 학생을 등록해 주세요." (시나리오1은 "학원셋팅을 완료해 주세요.")
- **시나리오2 개선 후 지문**: 1번(클래스 생성·학생 등록)은 없다. 지문은 ① 청구서 생성 ② 청구서 발송 ③ 학생 1명 추가 등록 후 출석 (번호는 자동). 개선 전은 3개(클래스 생성·학생 등록 / 피드 / 출석).
- **시나리오2 개선 후 1번 지문**: "신규 원생의 청구서를 발생해야 합니다. 청구서 관리 기능을 통해 청구서를 생성해 주세요."
- **시나리오2 개선 전 1번 지문**: "클래스와 학생을 등록/생성하여 학원 셋팅을 완료해 주세요."
- **데이터 초기화 확인 문구**(시나리오 1·2, 개선 전/후 동일): "데이터를 초기화 하시겠어요?" (아니오/예)
